### HAP Scheduler

The **HAP** scheduler is a **multi-start metaheuristic scheduler** for astronomical observations. Its design goal is to balance solution quality and computation time, stay flexible under changing constraints, and search promising parts of the solution space first. The paper describes it as a **repair-based** method with a **Tabu-search-like core** and a **multi-start layer**. 

At a high level, HAP works on **two levels**. The lower level is the **CRU** (**Conflict Resolution Unit**), which handles scheduling at the **task** level. The upper level is **HAP** itself, which works at the **scheduling-block** level: it decides which blocks to process, runs several CRUs in parallel, compares their results, and keeps the best schedules. A scheduling block is a set of dependent tasks, and the scheduler’s main objective is to complete as many valuable blocks as possible while also maximizing science time. 

The **CRU** is the local repair engine. It receives a non-empty set of tasks, a current schedule, and a few parameters. It puts the input tasks into a waiting list called the **Lobby**. Then it repeatedly picks one task from the lobby and tries to place it into the schedule. For each feasible time window of that task, it computes the **conflict group**: the tasks already scheduled that overlap this window. It then computes the **cost** of using that window, based on how much scheduling-block value would be damaged if those conflicting tasks were removed. If it finds a conflict-free window, it places the task there immediately. Otherwise, it makes a **stochastic choice** among the low-cost windows, places the task, removes the conflicting scheduled tasks, and pushes those displaced tasks back into the lobby to be rescheduled later. CRU also remembers the best intermediate schedule it has seen, because temporarily worsening the situation can help it escape a local minimum. 

That means CRU is not a simple greedy inserter. It is a **repair search**: insert a task, break the least valuable conflicts, reinsert what got displaced, and continue until the lobby is empty or the iteration limit is reached. The paper explicitly says CRU always returns a schedule containing the input tasks, with overlapping old tasks removed or repaired, and that its search follows a **Tabu-search methodology**. 

Above CRU, **HAP** coordinates multiple CRUs at once. It starts from a set of schedules and a subset of scheduling blocks still to process. For each available CRU, HAP selects a base schedule, then **accumulatively** adds the selected blocks by repeatedly calling the CRU. Each CRU produces candidate schedules. HAP collects all of them, evaluates them, and keeps the most competent ones for the next iteration. Then it updates the set of remaining blocks and repeats. Increasing the number of CRUs increases **exploration**; increasing the CRU iteration limit increases **exploitation**. 

The default evaluation in HAP uses two fitness functions. One rewards **scheduling-block completion weighted by block priority**. The other rewards **time spent on science tasks**. So the algorithm is always trying to trade off two things: completing high-value blocks and using the telescope efficiently. The paper notes that the evaluation module can be customized, but these two are the base objectives.

So the simplest description is this: **HAP repeatedly chooses scheduling blocks, lets several CRUs try to insert their tasks by repairing conflicts, scores the resulting schedules, keeps the best few, and continues until the block set is processed.** The novelty is the combination of a task-level repair mechanism and a higher-level multi-start selection process, which gives both flexibility and search diversity.
